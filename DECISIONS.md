# SplitBot: decisions log

## Summary

### The 5 most important decisions
1. **The LLM extracts; code calculates.** Gemini returns structured tool arguments, and tested TypeScript computes every share, balance and transfer. Trade-off: the tool schemas are more detailed, but a total can't be hallucinated and the logic can be unit tested.
2. **Every expense and payment goes through a draft.** Nothing the model produces is saved until I click Confirm. Trade-off: one extra click per expense, in exchange for catching model mistakes before they're saved. Deletes, creating a group and adding a member write directly, as approved exceptions, because they have nothing to preview or move no money.
3. **Guardrails warn, but block guesses about who took part.** Suspicious amounts and names become warnings on the draft, so I stay in control. `UNNAMED_PERSON` and `SPLIT_COUNT_MISMATCH` reject the tool call in the agent path, because prompt rules and warnings didn't stop the model guessing. Trade-off: "split with everyone" is rejected and the model has to ask.
4. **Integer cents, with leftover cents going to the payer first.** This avoids floating-point drift, and shares always add up exactly to the total. Listed order alone gave different results for the same expense, because the AI picks the order. Trade-off: the split engine now needs `paidBy`.
5. **A JSON file, single user, no login.** There are no native modules and nothing to set up, which kept the time on the agent and the money logic. Trade-off: no SQL, so summaries are computed in memory, and a host with an ephemeral disk would lose the data.

### The 5 clearest times the AI got it wrong
1. **Caught by writing a test: a name rule that broke the plan's own example (Step 2).** The AI recommended that the shorter name set the close-name threshold, and I approved it. Writing the tests showed that "Aroon" vs "Arun" would then get no warning. Done: the longer name now sets the threshold.
2. **Caught by the eval: the model guessed a participant (Step 4).** "Uber $24 Mei paid split 3 ways" should have produced a question, but the model filled in the third person from the known-people list. Reruns showed that a prompt fix didn't hold and that the first code guard couldn't catch a wrong count. Done: `UNNAMED_PERSON` and `SPLIT_COUNT_MISMATCH` now enforce this in code.
3. **Caught by `/review-step`: an infinite loop behind passing tests (Step 2).** All 120 tests passed, but a probe showed that `spendingSummary` looped forever on a malformed date (`2026-1-05`) and that month-only bounds silently dropped data. The tests had only used valid dates. Done: dates must be real YYYY-MM-DD dates, with regression tests.
4. **Caught by my browser check: invented dates (Step 5).** Drafts showed 27/10 and 26/10 on 4/11, though I never mentioned a date and the prompt said to leave it out. Neither the tests nor the eval checked dates. Done: code drops the model's date unless a user message contains a date phrase, and the draft then uses today.
5. **Caught by GitHub: a real Gemini key in `.env.example`.** I'm not certain how it got there, but most likely I pasted the key in myself when updating the model name, instead of into `.env`. The AI's part was missing it: the file is committed, so the key ended up in a local commit, and none of the tests or reviews caught it. GitHub push protection blocked the push, so it never reached GitHub. Done: I removed the key, amended the commit and rotated the key. `server/test/env-example.test.ts` now fails if the file contains a key.

## Decisions & trade-offs
- **Store data in a JSON file, not SQLite or Postgres.** For one user, the simplest storage is enough: no native modules and nothing to set up. Trade-off: no SQL queries, so summaries are computed in memory, and free hosts with ephemeral disks would lose the data. Writes are atomic (write a temp file, then rename) and go through a queue so concurrent writes can't corrupt the file.
- **Single user, no login.** People are just names, and the user is the built-in person `me`. This keeps 1.5 days focused on the agent and the money logic.
- **The LLM extracts; code calculates.** Gemini returns structured tool arguments, and `computeShares` and the balance and settle-up code do every calculation. Trade-off: the tool schemas are more detailed, but money totals can't be hallucinated and the logic is unit testable.
- **Integer cents with a deterministic leftover-cent rule.** This avoids floating-point drift. Shares always add up exactly to the total, and leftover cents go to whoever is listed first.
- **Leftover cents go to the payer first (Step 1).** Ties in the largest-remainder split go to the payer if they're a participant, then in listed order. The participant order comes from the AI and can vary between phrasings, so listed-order alone gave different results for the same expense; the payer is stable. Trade-off: the engine now needs `paidBy`. 0% and exact 0 are allowed.
- **Split engine strictness (Step 1 review).** Percent tolerance (±0.01) is checked on the raw percentages, then allocation uses integer weights in millionths of a percent. Values for a different split type (e.g. `percent` on an `equal` split) are rejected with `SPLIT_VALUES_TYPE_MISMATCH` so the agent gets feedback instead of a silent 50/50; an empty map is treated as absent. Share counts allow at most 3 decimals. Every money error message is in dollars, including invalid inputs like `$1.005`.
- **Greedy settle-up, not true minimum (Step 2).** Settle-up matches the largest creditor with the largest debtor. It always clears every balance in at most n−1 transfers, but finding the true minimum number of transfers is NP-hard, and greedy can miss it in rare cases. For a small group the difference is at most a transfer or two, so the simple, predictable method wins. PLAN.md now calls it "greedy settle-up (at most n−1 transfers)" instead of "minimum-transfers".
- **Structured draft warnings (Step 2).** `Draft.warnings` changed from `string[]` to `{ code, message, suggestion? }[]`, so the DraftCard can show a "Use Arun" button without parsing text. `suggestion` is `{ name, person }`: the name that was typed and the existing person to use instead.
- **Amount check covers exact splits; zeros are skipped (Step 2).** Exact amounts are checked like the total, percentages and share counts. Values of 0 (exact 0, 0%) aren't checked, because "Mei owes nothing" usually has no number in it.
- **Close-name rules (Step 2).** The short-name threshold (≤1 instead of ≤2) uses the longer of the two names, so the check is symmetric. The prefix rule means one name starts with the other and the shorter one has at least 3 letters (Rob/Robert).
- **Summary input is strict (Step 2 review).** `from`, `to` and every expense date must be a real YYYY-MM-DD date, and every category must be in `CATEGORIES`; otherwise a `RangeError` is thrown. Month-only bounds like `2026-10` are rejected rather than guessed at, so the agent has to send full dates.
- **The user's own name counts as an exact match (Step 2 review).** `me` is never offered as a suggestion, but typing me's display name (e.g. "Rahul") doesn't produce a warning about someone similar.
- **One write path: drafts (Step 3).** PLAN.md had `POST /api/expenses` saving a manual expense directly. It was dropped. The manual form and Settle up's "Record" call `POST /api/drafts` and then confirm, so CLAUDE.md principle 3 holds without exceptions. Trade-off: two requests for a manual save.
- **Draft editing and settlement routes (Step 3).** Added `PATCH /api/drafts/:id` (edit + recompute without saving; the DraftCard needs it) and `GET`/`DELETE /api/settlements` (the History panel needs them). PATCH and confirm share `applyEdits`. PATCH restarts the 30-minute TTL, because editing means the user is still working on it.
- **Provisional `new:` ids for people who don't exist yet (Step 3).** In a draft, "Kai" is `new:kai` and `newPeople` is `Person[]`. On Confirm, each one becomes a real nanoid id, or an existing person with the same name if another confirm created them first; the id is swapped in the payer, shares, adjustments and split maps. Chosen over slug ids so stored ids don't depend on spelling. The finalize step runs inside the store's write queue, so two drafts that both add "Kai" end up with one Kai.
- **Edits and warnings (Step 3).** After an edit, `CLOSE_NAME` warnings stay only for new people still in the draft ("Use Arun" removes Aroon's). An amount edit clears `AMOUNT_NOT_IN_MESSAGE` warnings, because the user has now entered the amount themselves; other edits keep them.
- **Store details (Step 3).** The cache is updated only after the rename succeeds, so a failed write changes nothing, and the queue keeps going after a failure. A corrupt or wrong-shaped db.json makes startup fail rather than being overwritten. The seed name for `me` is "Me". REST money is integer cents (the client converts).
- **No payer mentioned → me (Step 4).** "rent 1800 split 60/40 with Arun" is a draft with me as payer, not a question, which is how Splitwise behaves and how PLAN's eval sentence reads. The agent still asks when a payer is mentioned but unclear ("he paid"). "60/40 with Arun" gives the first number to me. This narrows CLAUDE.md principle 4, which now says so. The draft still needs Confirm, so a wrong default is caught there.
- **"Split 3 ways" with only one other name → ask (Step 4).** Filling in the third person from known people would be a guess. The eval has both the vague sentence (expects a question) and one naming all three.
- **Amount check against every user message (Step 4).** After "Who paid?" → "I did", the latest message has no numbers, so checking only it would always warn. Trade-off: a number from an earlier message can hide a wrong amount. PLAN said "latest message"; changed.
- **Tool arguments in dollars, split values as arrays (Step 4).** The model passes amounts as typed (`totalDollars: 90`), and the server runs `toCents`, so the model never multiplies by 100. Split values are `[{ person, … }]` arrays because Gemini schemas handle free-form maps badly; a name listed twice is an error instead of a silent overwrite.
- **Tool results are pre-formatted (Step 4).** Read tools return names and "$38.00" strings plus summaries like "Arun owes you $38.00", so the model has nothing to compute; the prompt says to quote tool results only.
- **Gemini errors (Step 4).** 429/5xx/network → a normal reply ("try again in a moment") that keeps drafts already made; no key → 503 `GEMINI_NOT_CONFIGURED` while the rest of the API works; other API errors → 500, logged with status and Google's message only.
- **Model: gemini-3.5-flash-lite (Step 4).** `gemini-2.5-flash` (the planned default) now answers 404 "no longer available to new users" even though it still shows up in the model list. Its suggested replacement, `gemini-3.8-flash`, has only about 20 free requests a day, which one eval run would use up. `gemini-3.5-flash-lite` allows about 500 a day on the free tier. Checked that the key can use it by listing models (names only, key not printed). It's the default in code and `.env.example`; I update my own `.env`.
- **The loop keeps the model's turn as-is (Step 4).** The raw `content` (with 2.5+/3.x thought signatures) is sent back, not rebuilt from the function calls, because Gemini rejects follow-up turns without the signatures.
- **Only people the user named, enforced in code (Step 4 eval).** The prompt rule for #2 didn't hold: the model made a draft and asked at the same time. `create_expense_draft` and `create_settlement_draft` now return `UNNAMED_PERSON` for any payer or participant (other than me or me's display name) whose name isn't in the user's messages, e.g. "Mei is the only person the user named (Arun wasn't mentioned). Ask the user who else is included." A name counts if it's a word or phrase in the text or a close spelling of one (`findCloseName` rules), ignoring pronouns and common words, so "split with me" doesn't name Mei and "and" doesn't name Ana. Trade-off: "split with everyone" is rejected and the model has to ask. Pure function `unnamedPeople` in guardrails.ts, tests #74–#80; tool tests #47–#52.
- **"N ways" must match the participant count, enforced in code (Step 4 eval).** Even with the named-people rule, #2 failed 3/3: the model drafted me + Mei for "split 3 ways", and both of those people are named, so `UNNAMED_PERSON` couldn't catch it. `create_expense_draft` now returns `SPLIT_COUNT_MISMATCH` when a user message says "N ways" (digits, two–ten as words, "3-way", "4 way split"; the last mention wins) and the number of distinct participants differs, e.g. "The user said 3 ways but only 2 people are included. Ask who the other person is." Pure `splitWays` in guardrails.ts (tests #81–#85), tool tests #53–#55. The `description` and `category` schema descriptions are also clearer (required, exact enum spelling, which category hotels, rent and taxis go in), aimed at #7's first call failing validation. I haven't seen that call's error, so that part is a guess for the eval to confirm.
- **Fixture update for the `UNNAMED_PERSON` rule (Step 4), not a weakened test.** Tool tests #5, #6 (tickets) and #7 used user texts that never mentioned the people in their tool arguments ("Coffee 12.5", "tickets $150 split 2:1", "rent 1800 split 60/40"), which the new rule rightly rejects. The requirement changed, so only those texts changed, gaining the names ("… with Arun and Mei", "… with Arun"). No amount and no assertion changed, and each test still checks what it did before (cents conversion, split arrays, duplicate names). Approved by me before the edit.
- **Drafts before writes.** The agent can never save directly; the user confirms every expense or settlement. Trade-off: one extra click per expense, in exchange for safety when the model gets something wrong.
- **5 tool calls per message.** This prevents runaway loops and protects the free-tier quota.

Since Step 4, `UNNAMED_PERSON` and `SPLIT_COUNT_MISMATCH` do block, but only in the agent path: they catch the model guessing who takes part, which a warning didn't stop, and the model has to ask instead. `POST /api/drafts` (the manual form) doesn't run them.

- **Step 7 lite: docs only (Step 7).** This step is the README and this summary, with no new features. The manual expense form and the README screenshots that PLAN.md lists for Step 7 are left out. Trade-off: without a working Gemini key or quota, the UI can't add an expense.
- **MongoDB behind the same interface, with a cache (Step 9).** `snapshot()` is sync, so a Mongo store has to serve it from memory. I chose this over making the store async, which would have changed about 20 read sites, sync `runTool` and about 35 test lines. Trade-off: all data is in memory, and the indexes do little today. Only `/api/summary` with a date range queries Mongo, and the UI and agent don't send one. The `groupId` index has no caller yet.
- **Revision check before each request (Step 9).** I added this for Vercel: `/api` middleware reads `meta.revision` and reloads only if another instance has written, which keeps `snapshot()` sync. It adds one small read per request, so seven per dashboard refresh. If the check fails, the request answers from the cache, so a read can be stale during an outage. A write from stale data still gets a 409 `STORE_CONFLICT`, and the draft is restored.
- **Drafts don't work across instances (Step 9).** The revision check covers saved data only. Drafts are in memory, so a Confirm that reaches another instance gets 404 `DRAFT_NOT_FOUND`. Test #M15 documents this, and the two-process check showed it too. Serverless hosting needs shared drafts before it can work.
- **Uncertain commits (Step 9).** Each transaction records its id in `meta.recentTxnIds`, the last 20. After an error, that id says whether the commit applied, so a lost reply doesn't cause a retry that saves a duplicate. Known gap: if the read-back fails too, the save is reported as failed even if it applied, and a retry can duplicate it. The next check does load the committed data.
- **No fallback and no secrets in errors (Step 9).** A bad `STORE` or a missing URI stops startup, because falling back would save to the wrong place. Mongo errors keep only the driver error's type and code, because its messages can hold hosts or the URI. The database is always named `splitbot`, so an Atlas URI with no database name doesn't write to the driver's default `test`.
- **Filtered summaries validate less (Step 9).** With a date range, `/api/summary` validates only the expenses the range filter keeps, and that filter compares dates as text. So a malformed date can be dropped even inside the range it really belongs to, and the answer is wrong rather than an error: an expense dated `2026-1-05` gives 200 with total 0 for `?to=2026-01-31`, because `2026-1-05` sorts after `2026-01-31`. The same expense still gives a 400 with no range or with `?from=2026-01-01&to=2026-11-30`. The agent's summary tool still validates everything, so it can disagree with REST on the same data. Only a hand-edited database can contain such a date. This applies to both stores, and test #A5 pins it as a known limit.
- **Forced exit on shutdown (Step 9).** The signal handlers I added in this step meant a stuck request could stop the process exiting, in JSON mode too. `server/src/shutdown.ts` now closes the server and then the store, and exits 1 if that takes more than 10 seconds. Second Ctrl-C still kills it straight away. Trade-off: a request still running at 10 seconds is cut off, but a save either commits or rolls back.
- **Cut for time (Step 9).** I cut the db.json migration script, because I'm starting with fresh data, and the `explain()` index tests. So `#M3` checks that the indexes exist, not that queries use them.
- **Deploy: frontend on Vercel, API on one Render instance (Step 8 plan).** Vercel rewrites `/api/*` to Render, so the browser calls its own origin and CORS doesn't change. Data lives in Atlas, because Render's free disk is ephemeral. I chose this over running the API on Vercel, which would have needed drafts moved into Mongo plus a handler wrapper. Trade-off: one instance and in-memory drafts, so a Render restart loses open drafts, but saved data is safe. The revision check stays, though with one instance it has little to do.
- **Supported timeouts instead of `timeoutMS` (Step 9).** The driver has deprecated `timeoutMS` and ignores it. It now uses `connectTimeoutMS` 5 s, `socketTimeoutMS` 15 s, `waitQueueTimeoutMS` 5 s and `maxCommitTimeMS` 10 s, with server selection at 5 s as before. Measured with a real `mongod` behind a proxy that went silent: a write failed after 10 s, the first request's check took 20 s, and later checks took 5 s each before answering from the cache. Trade-off: these limit each step, not a whole operation. The driver's `withTransaction` can keep retrying transient errors for up to 120 s, though it didn't in this run.
- **Known limitations (Step 9).** Uncertain commits are tested through injected failures, not real driver error labels. The stalled-database delay is real: while the database is unresponsive, every `/api` request waits for the check first, about 20 seconds for the first and about 5 seconds each after that, so the app is slow rather than down, and a dashboard refresh makes seven calls. Those numbers come from one run of a throwaway probe. Tests not written, from the `/review-step`, to keep to the time box: a stale `DELETE /api/expenses/:id` or `POST /api/groups` answering 409 with nothing changed; a silent connection making `update()` reject with `StoreError` and the snapshot unchanged, within a set limit (the only timeout test is #M20, no deprecated option); and `/api/summary` answering 500 `INTERNAL`, with no driver message in the response or log, when the Mongo query fails. A fresh offline clone can't pass `npm test`, because the Mongo tests need the downloaded binary, and I chose that over skipping them. `concurrently` asks for Node 22 and warns on Node 20; this was already the case and it still runs.
- **Redesign keeps every existing test unedited (Step 10).** I made that a hard rule, and some tests pin markup. So `#54` and `#55`, which pin the exact person `<li>`, force a nested `<ul role="none">` to fit an avatar. Trade-off: slightly awkward markup, in exchange for proof that the redesign changed no behaviour those tests cover. Loosening the two assertions is the alternative if it ever gets in the way.
- **Avatar initials through CSS (Step 10).** They come from `data-initials`, because the tests read sentences like "Arun pays you $39.00" as continuous text, and screen readers should too. The avatar is decorative, since the name is always written beside it.
- **Category colours are a rotation of the dataviz reference palette (Step 10).** It passes the validator in both themes in `CATEGORIES` order. Bars are sorted largest first (`#104`), so any two hues can still touch, and no 8-hue palette clears the all-pairs floor. Every bar therefore keeps a text label, its value and the table view, so colour never identifies a category alone. Eight hues also overlap the status colours (orange, red, green), so chips always carry an icon and a name.
- **`lucide-react` only, no `motion` (Step 10).** CSS covers the motion, apart from list removal, which gets a small hook. No jsdom either: render tests use `renderToStaticMarkup` like the existing ones, and interactions are checked in headless Chrome.
- **Inter from Google Fonts (Step 10).** This adds the app's first external request at page load; offline it falls back to the system font. Measured in Chrome: its digits really are tabular (`1111` and `0000` are both 83px wide at 32px).
