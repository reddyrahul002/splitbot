# SplitBot: decisions log

## Decisions & trade-offs
- **Store data in a JSON file, not SQLite or Postgres.** For one user, the simplest storage is enough: no native modules and nothing to set up. Trade-off: no SQL queries, so summaries are computed in memory, and free hosts with ephemeral disks would lose the data. Writes are atomic (write a temp file, then rename) and go through a queue so concurrent writes can't corrupt the file.
- **Single user, no login.** People are just names, and the user is the built-in person `me`. This keeps 1.5 days focused on the agent and the money logic.
- **The LLM extracts; code calculates.** Gemini returns structured tool arguments, and `computeShares` and the balance and settle-up code do every calculation. Trade-off: the tool schemas are more detailed, but money totals can't be hallucinated and the logic is unit testable.
- **Integer cents with a deterministic leftover-cent rule.** This avoids floating-point drift. Shares always add up exactly to the total, and leftover cents go to whoever is listed first.
- **Leftover cents go to the payer first (Step 1).** Ties in the largest-remainder split go to the payer if they're a participant, then in listed order. The participant order comes from the AI and can vary between phrasings, so listed-order alone gave different results for the same expense; the payer is stable. Trade-off: the engine now needs `paidBy`. 0% and exact 0 are allowed.
- **Split engine strictness (Step 1 review).** Percent tolerance (±0.01) is checked on the raw percentages, then allocation uses integer weights in millionths of a percent. Values for a different split type (e.g. `percent` on an `equal` split) are rejected with `SPLIT_VALUES_TYPE_MISMATCH` so the agent gets feedback instead of a silent 50/50; an empty map is treated as absent. Share counts allow at most 3 decimals. Every money error message is in dollars, including invalid inputs like `$1.005`.
- **Greedy settle-up, not true minimum (Step 2).** Settle-up matches the largest creditor with the largest debtor. It always clears every balance in at most n−1 transfers, but finding the true minimum number of transfers is NP-hard, and greedy can miss it in rare cases. For a small group the difference is at most a transfer or two, so the simple, predictable method wins. PLAN.md now calls it "greedy settle-up (at most n−1 transfers)" instead of "minimum-transfers".
- **Structured draft warnings (Step 2).** `Draft.warnings` changed from `string[]` to `{ code, message, suggestion? }[]`, so the DraftCard can show a "Use Arun" button without parsing text. `suggestion` is `{ name, person }`: the name that was typed and the existing person to use instead.
- **Amount check covers exact splits; zeros are skipped (Step 2).** Exact amounts are checked like the total, percentages and share counts. Values of 0 (exact 0, 0%) aren't checked, because "Mei owes nothing" usually has no number in it.
- **Close-name rules (Step 2).** The short-name threshold (≤1 instead of ≤2) uses the longer of the two names, so the check is symmetric. The prefix rule means one name starts with the other and the shorter one has at least 3 letters (Rob/Robert).
- **Summary input is strict (Step 2 review).** `from`, `to` and every expense date must be a real YYYY-MM-DD date, and every category must be in `CATEGORIES`; otherwise a `RangeError` is thrown. Month-only bounds like `2026-10` are rejected rather than guessed at, so the agent has to send full dates.
- **The user's own name counts as an exact match (Step 2 review).** `me` is never offered as a suggestion, but typing me's display name (e.g. "Rahul") doesn't produce a warning about someone similar.
- **One write path: drafts (Step 3).** PLAN.md had `POST /api/expenses` saving a manual expense directly. It was dropped. The manual form and Settle up's "Record" call `POST /api/drafts` and then confirm, so CLAUDE.md principle 3 holds without exceptions. Trade-off: two requests for a manual save.
- **Draft editing and settlement routes (Step 3).** Added `PATCH /api/drafts/:id` (edit + recompute without saving; the DraftCard needs it) and `GET`/`DELETE /api/settlements` (the History panel needs them). PATCH and confirm share `applyEdits`. PATCH restarts the 30-minute TTL, because editing means the user is still working on it.
- **Provisional `new:` ids for people who don't exist yet (Step 3).** In a draft, "Kai" is `new:kai` and `newPeople` is `Person[]`. On Confirm, each one becomes a real nanoid id, or an existing person with the same name if another confirm created them first; the id is swapped in the payer, shares, adjustments and split maps. Chosen over slug ids so stored ids don't depend on spelling. The finalize step runs inside the store's write queue, so two drafts that both add "Kai" end up with one Kai.
- **Edits and warnings (Step 3).** After an edit, `CLOSE_NAME` warnings stay only for new people still in the draft ("Use Arun" removes Aroon's). An amount edit clears `AMOUNT_NOT_IN_MESSAGE` warnings, because the user has now entered the amount themselves; other edits keep them.
- **Store details (Step 3).** The cache is updated only after the rename succeeds, so a failed write changes nothing, and the queue keeps going after a failure. A corrupt or wrong-shaped db.json makes startup fail rather than being overwritten. The seed name for `me` is "Me". REST money is integer cents (the client converts).
- **No payer mentioned → me (Step 4).** "rent 1800 split 60/40 with Arun" is a draft with me as payer, not a question, which is how Splitwise behaves and how PLAN's eval sentence reads. The agent still asks when a payer is mentioned but unclear ("he paid"). "60/40 with Arun" gives the first number to me. This narrows CLAUDE.md principle 4, which now says so. The draft still needs Confirm, so a wrong default is caught there.
- **"Split 3 ways" with only one other name → ask (Step 4).** Filling in the third person from known people would be a guess. The eval has both the vague sentence (expects a question) and one naming all three.
- **Amount check against every user message (Step 4).** After "Who paid?" → "I did", the latest message has no numbers, so checking only it would always warn. Trade-off: a number from an earlier message can hide a wrong amount. PLAN said "latest message"; changed.
- **Tool arguments in dollars, split values as arrays (Step 4).** The model passes amounts as typed (`totalDollars: 90`), and the server runs `toCents`, so the model never multiplies by 100. Split values are `[{ person, … }]` arrays because Gemini schemas handle free-form maps badly; a name listed twice is an error instead of a silent overwrite.
- **Tool results are pre-formatted (Step 4).** Read tools return names and "$38.00" strings plus summaries like "Arun owes you $38.00", so the model has nothing to compute; the prompt says to quote tool results only.
- **Gemini errors (Step 4).** 429/5xx/network → a normal reply ("try again in a moment") that keeps drafts already made; no key → 503 `GEMINI_NOT_CONFIGURED` while the rest of the API works; other API errors → 500, logged with status and Google's message only.
- **Model: gemini-3.5-flash-lite (Step 4).** `gemini-2.5-flash` (the planned default) now answers 404 "no longer available to new users" even though it still shows up in the model list. Its suggested replacement, `gemini-3.8-flash`, has only about 20 free requests a day, which one eval run would use up. `gemini-3.5-flash-lite` allows about 500 a day on the free tier. Checked that the key can use it by listing models (names only, key not printed). It's the default in code and `.env.example`; I update my own `.env`.
- **The loop keeps the model's turn as-is (Step 4).** The raw `content` (with 2.5+/3.x thought signatures) is sent back, not rebuilt from the function calls, because Gemini rejects follow-up turns without the signatures.
- **Only people the user named, enforced in code (Step 4 eval).** The prompt rule for #2 didn't hold: the model made a draft and asked at the same time. `create_expense_draft` and `create_settlement_draft` now return `UNNAMED_PERSON` for any payer or participant (other than me or me's display name) whose name isn't in the user's messages, e.g. "Mei is the only person the user named (Arun wasn't mentioned). Ask the user who else is included." A name counts if it's a word or phrase in the text or a close spelling of one (`findCloseName` rules), ignoring pronouns and common words, so "split with me" doesn't name Mei and "and" doesn't name Ana. Trade-off: "split with everyone" is rejected and the model has to ask. Pure function `unnamedPeople` in guardrails.ts, tests #74–#80; tool tests #47–#52.
- **"N ways" must match the participant count, enforced in code (Step 4 eval).** Even with the named-people rule, #2 failed 3/3: the model drafted me + Mei for "split 3 ways", and both of those people are named, so `UNNAMED_PERSON` couldn't catch it. `create_expense_draft` now returns `SPLIT_COUNT_MISMATCH` when a user message says "N ways" (digits, two–ten as words, "3-way", "4 way split"; the last mention wins) and the number of distinct participants differs, e.g. "The user said 3 ways but only 2 people are included. Ask who the other person is." Pure `splitWays` in guardrails.ts (tests #81–#85), tool tests #53–#55. The `description` and `category` schema descriptions are also clearer (required, exact enum spelling, which category hotels, rent and taxis go in), aimed at #7's first call failing validation. I haven't seen that call's error, so that part is a guess for the eval to confirm.
- **Fixture update for the `UNNAMED_PERSON` rule (Step 4), not a weakened test.** Tool tests #5, #6 (tickets) and #7 used user texts that never mentioned the people in their tool arguments ("Coffee 12.5", "tickets $150 split 2:1", "rent 1800 split 60/40"), which the new rule rightly rejects. The requirement changed, so only those texts changed, gaining the names ("… with Arun and Mei", "… with Arun"). No amount and no assertion changed, and each test still checks what it did before (cents conversion, split arrays, duplicate names). Approved by me before the edit.
- **Drafts before writes.** The agent can never save directly; the user confirms every expense or settlement. Trade-off: one extra click per expense, in exchange for safety when the model gets something wrong.
- **5 tool calls per message.** This prevents runaway loops and protects the free-tier quota.
- **Guardrails warn, never block, with two agent-only exceptions.** Amounts that aren't in the message and close-but-different names produce warnings on the draft rather than errors, so the user stays in control. Since Step 4, `UNNAMED_PERSON` and `SPLIT_COUNT_MISMATCH` do block, but only in the agent path: they catch the model guessing who takes part, which a warning didn't stop, and the model has to ask instead. `POST /api/drafts` (the manual form) doesn't run them.
- **Step 4 review fixes.**
  - "N ways" now counts only for the expense being drafted (the latest user message with a number, plus any after it), so "split 3 ways" from an earlier expense no longer blocks a later 2-person one. Only "N ways" / "N-way split" count, so a "3-way adapter" doesn't.
  - Cents must be safe integers in `computeShares` (a $1e15 total used to lose 4 cents without an error), and every dollar argument is capped at 1,000,000.
  - Gemini calls time out after 20 s and get the busy reply.
  - `SplitError` messages name people ("Kai") instead of quoting ids like `new:kai`, for REST as well as the model.
  - A bad key or unknown model is a 502 with `GEMINI_KEY_INVALID` / `GEMINI_MODEL_UNAVAILABLE` and a message the UI can show, not a generic 500.
- **Test #42 assertion updated for a requirement change (Step 4 review), not weakened.** Its 403 branch asserted the old generic 500. The review's fix 6 replaced that behavior, so it now expects 502 `GEMINI_KEY_INVALID`. That's stricter: it checks the code, not just the status. The key-secrecy assertions are unchanged. I asked for this fix.
- **Known limitations (Step 4).**
  - Name matching is lenient: an invented name passes `UNNAMED_PERSON` if it's a close spelling of an ordinary word in the message. "Sam" passes because of "same" (prefix rule), "Ari" because of "are", and "Will" because "will" is also a verb. The guard catches names that aren't in the message at all, not every guess.
  - The amount check (and the named-people check) read every user message in the chat, so a number or name from an earlier expense can hide a wrong one in a later draft. Only the "N ways" check is limited to the current expense.
- **Chat history kept on the client.** The server is stateless apart from short-lived drafts, which keeps it simpler.
- **Local only.** Deploying to Render + Vercel is a stretch goal (Step 8).
- **Money helpers moved to `shared` (Step 5).** The DraftCard has to parse typed dollars and format cents, and a copy in the client could drift from the server's rounding. `server/src/domain/money.ts` re-exports them, so server imports and `money.test.ts` didn't change. Splitting money still happens only on the server.
- **New people are dropped when they leave a draft (Step 5).** "Kai paid $30, split with me and Mei", then changing the payer to me, used to create Kai on Confirm. The new payer dropdown made this easy to hit, and it broke "nothing is created that you didn't see". Trade-off: Kai also leaves the payer list for that draft, so undoing means discarding the draft and asking again.
- **`GEMINI_NOT_CONFIGURED` no longer mentions the form (Step 5).** The form is Step 7 and may be cut for time, so the message shouldn't promise it. Restore the sentence only if the form gets built.
- **Vite proxy instead of CORS calls (Step 5).** The client calls `/api/...` on its own origin. The proxy reads only `PORT*` from the root `.env`, using Vite's env prefix, so the Gemini key never enters the Vite process's config.
- **Client tests cover pure logic and fetch wrappers only (Step 5).** No jsdom or testing-library, to stay lean. The components themselves are checked by the browser walkthrough, so a rendering bug won't fail `npm test`.
- **Edits run one at a time per card (Step 5).** Typing an amount and clicking Confirm fires a PATCH and a confirm together, and the wrong order could save the old amount. Confirm waits for the edit and doesn't save if it failed.
- **The model's date needs a date phrase in any user message in the chat (Step 5 review).** Applies to expenses and payments, in the agent path only. I chose this simple rule over trying to work out which messages belong to the current expense, which lost dates the user had stated. Trade-off: an older date phrase can let a wrong date through, but the date is always visible and editable on the card. A false match only keeps the model's date, so `hasDatePhrase` leans towards matching; short days and bare months need a lead-in ("on sat", "in may"), so "I sat with Mei" and "Lunch with April" don't count. `27-10` and `27.10` count, but not `60-40`, `60.40`, `$27.10` or `12.25`.
- **`NAME_RESPELLED` is a separate warning, not `CLOSE_NAME` (Step 5 walkthrough).** `CLOSE_NAME` means "this new name looks like an existing person, use them?" and drives the "Use Arun" button. This one reports a change the model already made, possibly to an existing person, so there's nothing to swap and the card shows no button. It's added only in the agent path, stays through amount edits, and goes when the person leaves the draft. Known limitations: if the spelling is wrong, the fix is to discard the draft and ask again, and an exact spelling in any earlier message of the chat means no warning.
- **New people's names are capitalized when the draft is built (Step 5 walkthrough).** Doing it at the draft, not just at Confirm, means the card and warnings show the name that will be saved. Only first letters change (also after a space or hyphen), so "McDonald" and "MEI" stay as typed. Existing people keep their stored spelling.
- **Hand-written markdown subset, no library (Step 5 walkthrough).** Bold, italic and lists only, parsed into plain data that React renders as text, with no `dangerouslySetInnerHTML`. Raw HTML stays visible text and links aren't parsed. Only model replies get it; user messages and errors stay plain.
- **Test #25 expected name updated for a requirement change (Step 5 walkthrough), not weakened.** It asserted a new person named `constructor` keeps that spelling. I asked for new names to be capitalized, so it now expects `Constructor`. The id and shares assertions, which are the point of the test (a prototype key is just a name), are unchanged. The AI made the edit first and told me afterwards, which CLAUDE.md says it shouldn't do; I reviewed and approved it after `/review-step`.
- **Tools test #67 reversed for a requirement change (Step 5 review).** It asserted that a date phrase from an earlier expense doesn't count. My "any user message" rule reverses that on purpose, so it now expects the model's date to be kept, with a comment naming the trade-off, and gained two follow-up cases. I asked for this rule; the test had only existed since the walkthrough fixes. I approved the edit after it was made.
- **After a failed edit, the first Confirm stops (Step 5 review).** A server rejection can arrive before the mouse button comes up, with the field already back to the old value, so Confirm used to save that and clear the error. Now a failure is remembered: the first Confirm stops and shows the error, and a second click saves the values shown. A later successful edit also clears it, on my reading that the values shown are then valid and a stale error would only mislead. Trade-off: one extra click after a rejection.
- **Client test #14 reversed for a requirement change (Step 5 review), not weakened.** It asserted "an old failure does not block a later Confirm", so the first click after a rejection wouldn't be lost. That behaviour is exactly what let Confirm save after a rejection, so I asked for the opposite: it now expects the first Confirm to stop and the second to go through. #41–#44 cover the rest.
- **Known limitations (Step 5 review).** Logged, not fixed, to keep to the time box:
  - A huge amount like `99999999999999999999` passes the client check and the server rejects it, probably with a raw validation message.
  - False date matches: "paid Jan 20", "split 1/2", "Rent 10/20", "$30 at 7/11", "60-40"-style splits with possible values such as "2-1" or "30-10", and a bare amount like "12.10" all count as date phrases, so an invented date gets through for those.
  - Any date phrase accepts whatever date the model sends: "Lunch today" with a model date of 27/10 stays 27/10.
  - Dates still not recognised, so they become today: "Lunch fri", "2 days back", "the other day", "October rent".
  - Markdown: `***x***` leaves a stray `*`, and an indented continuation line splits a list in two.
  - Capitalizing: `o'brien` becomes `O'brien`, and `van der berg` becomes `Van Der Berg`.
  - After one card creates Kai, another open card with new Kai shows two Kais in its payer list. Choosing either should save correctly.
  - Hand-checked only: the DraftCard and Chat components have no automated tests, and chips have no test at all. The eval hasn't been rerun since these agent changes and has no date check.
- **Three-column redesign replaces the old panels (Step 6).** Step 6 now merges the essentials of the old Steps 6 and 7, in parts the user can stop after: layout and account summary, Smart settle up, Expenses, Charts, and optional Groups. A horizontal bar replaces the planned donut. Step 7 keeps the manual form, README and screenshots.
- **`directDebts` cancels circular debts (Step 6).** A probe of the real domain functions showed that plain `pairwiseDebts` goes wrong once suggested payments are recorded: with everyone's net at $0 it still reported me→Arun, Arun→Mei and Mei→me at $15 each. Showing only settle-up amounts on the left would fix that, but one of "You are owed" and "You owe" would always be $0, and Arun's $38 would read $53. Cancelling circles keeps direct debts and clears them after settling. The account summary and `get_balances` use it, so the chat matches the panel; `/api/balances` keeps raw `pairwiseDebts` for now because no panel reads it.
- **`domain/account.ts` holds the summary maths (Step 6).** The totals, counts and payments saved had no home. A small domain module on top of the existing functions keeps the client free of maths.
- **"Minimum" stays out of the UI (Step 6).** `suggestSettlements` is greedy. In one probe, 3 direct debts became 4 transfers, so the savings note appears only when the saving is above 0.
- **Exceptions to "every write goes through a draft" (Step 6).** Delete writes directly, behind a two-click confirm, because there is nothing to preview. Creating a group (if Part E is built) also writes directly, because it moves no money.
- **Settle-up plan has its own route (Step 6 Part B).** The plan had the saving as extra fields on `Account`, which would have meant editing Part A's exact-shape tests. `settlePlan` and `GET /api/settlements/plan` leave them alone, and `GET /api/settlements/suggest` keeps its shape for existing callers.
- **One Record payment draft at a time (Step 6 Part B).** The buttons are disabled while a card is open, so a second click can't open a second card, and the list can't go stale behind one. The card sits above the list, so it stays visible if a transfer changes while it's open. Known gap: tabs mount only the active panel, so switching tabs drops the open card. Nothing is saved, and the server draft expires by its TTL.
